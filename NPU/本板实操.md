## 三、已跑出的实测数据

### 3.1 NPU 推理链路（`resnet18_for_rk3588.rknn`，224×224，官方模型）

```
load_rknn   : 0
init_runtime: 0
output0: (1, 1000) argmax: 812      # ImageNet 812 = space shuttle，图片正是航天飞机 → 结果正确
RESULT: 214.37 fps (4.66 ms/frame，默认单核)
运行时: librknnrt 2.3.2  |  驱动: 0.9.8  |  模型 toolkit 2.3.2 / target rk3588
```

### 3.2 core_mask 单进程延迟（200 次平均，验证 §7.2 的绑定是否真生效）

| core_mask | 单帧延迟 | 等效 fps |
|---|---|---|
| 1（CORE_0）| 5.054 ms | 197.9 |
| 2（CORE_1）| 5.145 ms | 194.4 |
| 4（CORE_2）| 5.707 ms | 175.2 |
| 1\|2（双核）| 3.427 ms | 291.8 |
| **1\|2\|4（三核）** | **2.965 ms** | **337.3** |

结论：**core_mask 真的生效**，三核相比单核延迟降到 59%（≈1.7×）。三个单核数值接近，说明三颗 NPU 核心是等价的。

> 注：这里是 **Python 侧**测的，含解释器开销；纯硬件时间见 `线程数饱和点.md`（ResNet18 单核 **3.82 ms**）。

### 3.3 多进程吞吐（`core_mask_bench.py`，各配置跑 5 s）

| 配置 | 进程数 | 总吞吐 |
|---|---|---|
| 默认（不传 mask）| 1 | 189.7 fps |
| 默认（不传 mask）| 3 | **554.3 fps** |
| 三核 mask=1\|2\|4 | 3 | 451.2 fps |
| 三核 mask=1\|2\|4 | 6 | 440.8 fps |

跑完三核负载 `Core0: 87%, Core1: 74%, Core2: 74%`。

> ⚠️ **这组数字别照抄进报告**，它有三个坑（也正是文档 §7.3 想说的那件事）：
> 1. **模型太小**：单帧 5 ms 里绝大部分是 Python/API/内存开销 → 加进程主要是在"掩盖宿主开销"，不是在分 NPU 算力。
> 2. **"3 进程 554 fps" 反直觉**：3 个不传 mask 的进程都只在 core0 上，却比单进程高 2.9×，说明驱动在做请求交织/流水，core0 远未跑满——真实瓶颈在宿主侧。
> 3. 三核绑定反而比不传 mask 低（451 vs 554），进一步坐实"**瓶颈不在 NPU 算力**"。
>
> 想复现文档里 119→181 fps 那种量级，得换成 **YOLOv5s 640×640** —— 见第四节。

## 四、§7–§9 性能压榨主线完整复现（2026-09-14 实测）

> 这是整篇技术文档的高潮章节。此前本板只有 ResNet18 / MobileNetV1 的小模型数字（见 3.2 / 3.3），
> **§7–§9 用文档指定的 YOLOv5s 640×640 模型从未真正跑过**。本节把它补上。
>
> **测试条件**：`yolov5s_relu.rknn`（8.39 MB INT8，本机 WSL 转换产物，MD5 `60a06747…`）；
> 全部按 §11 锁频（A55 1.8 G / A76 2.304 G / NPU 1.0 G / GPU 1.0 G / DDR 1.848 G）；
> 空闲 26.8 °C，全程峰值 **28.7 °C**。

### 4.1 完整演进链（对照文档 §9.1）

| # | 方案 | 程序 | 本板实测 | 文档值 |
|---|---|---|---|---|
| 1 | Python 单进程（不传 mask） | `board_stress_test_6p.py` | 38.0 fps | — |
| 2 | **Python 16 线程单核（反例）** | `board_stress_test_16t.py` | **28.2 fps** | 36 fps |
| 3 | Python 三核绑定 ×3 进程 | `board_stress_test_6p.py` | 107.1 fps | — |
| 4 | **Python 三核绑定 ×6 进程** | `board_stress_test_6p.py` | **118.7 fps** | **119 fps** |
| 5 | Python 三核绑定 ×9 进程 | `board_stress_test_6p.py` | 121.4 fps | — |
| 6 | C++ 单核单上下文 | `rknn_benchmark 1` | 15.98 ms / 62.6 fps | 18.8 ms / 53 fps |
| 7 | C++ 三核协同单上下文 | `rknn_benchmark 7` | 8.79 ms / 113.8 fps | — |
| 8 | C++ 零拷贝 3 线程 | `zero_copy_bench` | 173.6 fps | — |
| 9 | **C++ 零拷贝 8 线程** | `zero_copy_bench` | **177.6 fps** | **181+ fps** |

**结论：§7 与 §8 的两个关键数字都复现到文档值的 97%–100%** ——
16 线程反例 28.2 vs 36、六进程 118.7 vs 119、零拷贝 177.6 vs 181+。文档的三段式论断
（**锁竞争拖垮 → 多进程三核 → C++ 零拷贝**）在本板完整成立。

### 4.2 反例确认：16 线程确实比单进程还慢

| 配置 | 吞吐 |
|---|---|
| 单进程（1 个 RKNNLite，不传 mask） | **38.0 fps** |
| 16 线程共享 1 个 RKNNLite + 一把互斥锁 | **28.2 fps** |

-9.8 fps，方向与文档一致（文档是 53 → 36，-17 fps）。线程分布极不均匀
（`[43,13,25,18,19,13,14,27,22,15,12,20,14,15,18,10]`），正是抢锁的直接证据。
本板 CPU 更多（8 核）反而使切换开销更明显，掉得比文档还多。

### 4.3 ⚠️ 一处对文档结论的修正：**C++ 侧不需要「2:1 流水线」**

文档 §7.2 与视频笔记 §3.4 都用「数据准备阶段 NPU 会空转」来解释**为什么是 6 进程 / 8 线程**。
本板实测把这个理由的适用范围收窄了：

| 每核线程 | Python 多进程 | C++ 零拷贝（5 轮交错） | C++ 的逐核 NPU 占用 |
|---|---|---|---|
| 1/核 | 107.1 fps | 173.57 ± 0.09 fps | **96%** |
| 2/核 | **118.7 fps（+10.8%）** | **177.10 ± 0.32 fps（+2.0%）** | **98%** |
| 3/核 | 121.4 fps | 177.12 ± 0.14 fps | 98% |
| 4/核 | — | 176.86 ± 0.07 fps | 98% |

- **Python 侧流水线确实有效（+10.8%）** —— 瓶颈是解释器调度，加进程能掩盖宿主开销。
- **C++ 侧只有首步 +2.0% 是真实增益**：1 线程/核 达峰值 **98.0%**、NPU 占用 **96%**；
  加到 2 线程/核 补满这最后 2%（NPU 升到 98%）之后**再无收益**
  （6→8 = +0.12%，6→12 = −0.14%，均在噪声内）。
- 宿主 CPU 全程仅 **3.1–3.6%**，**排除宿主瓶颈**；对照 NPU 硬件上限（单核 16.00 ms → 三核并行
  理论上限 187.5 fps），零拷贝已跑到 **94.5%**。

**所以「2:1 配比」是 Python 的补救手段，不是普适原理。** 文档写成一般性结论会让人误以为
C++ 侧也必须开 8 线程 —— 实测表明 **6 线程（整数 2/核）与 8 线程等价（差 0.12%）**。

> ⚠️ 上表 C++ 一列是**严格复测值**，替换掉了本节早先的单轮 10 s 数据（173.6 / 176.7 / 177.5 / 176.7）。
> 完整数据、事先定死的判读规则、以及主实验首轮异常（142.67 fps）的交代，
> 见 `线程数饱和点.md`；原始采样在 `_archive/线程数饱和点-原始数据.zip`。
>
> **换成 ResNet18（单帧纯 NPU 仅 3.82 ms，比 YOLOv5s 快 4.2×）复测，曲线几乎重合**：
> 3 线程占峰值 **97.7%**（YOLOv5s 是 98.0%）、NPU 占用 96–97%。
> 即**饱和点与模型大小无关**，固定在 1→2 线程/核 之间。

### 4.4 零拷贝正确性已验证（不只是「跑得快」）

`zero_copy_bench.cc` 支持两种输入路径，实测输出校验和**逐字节相同**：

| pass_through | 输入数据 | out0 (1.63 MB) | out1 (408 KB) | out2 (102 KB) |
|---|---|---|---|---|
| 1（文档 §8.3 做法） | 自己量化成 INT8 | `sum=-193760164 nz=1630982` | `sum=-48731171 nz=407753` | `sum=-12269198 nz=101960` |
| 0（官方 demo 做法） | UINT8 交给 NPU | `sum=-193760164 nz=1630982` | `sum=-48731171 nz=407753` | `sum=-12269198 nz=101960` |

两个模式吞吐也几乎相同（175.8 vs 175.9 fps）。这证明：

1. 文档 §8.3 的 `pass_through = 1` 路径**确实可用且结果正确**；
2. 手写的量化映射 `int8 = uint8 - 128` 是对的
   （本模型 `zp=-128`、`scale=0.003922 ≈ 1/255`，故 `u/255/scale + zp = u - 128`）；
3. NPU 顺带做归一化+量化**不额外花钱**，所以两种写法性能等价。

> ⚠️ 该映射**只对 YOLOv5s 这个模型成立**。换模型必须按 `zp` / `scale` 重算 ——
> ResNet18 是 `zp=-13, scale=0.018478`，套 `-128` 就错了（所以对照实验用的是 `pass_through=0`）。

### 4.5 三核负载是均衡的

`zero_copy_bench` 按 `t % 3` 把线程轮转分给三个上下文。8 线程时各核实得帧数：

```
c0 = 3 线程 × 400 = 1200
c1 = 3 线程 × 393 = 1179
c2 = 2 线程 × 589 = 1178     ← 总 3557 帧 / 20.03 s = 177.6 fps
```

三核偏差 < 2%，说明 `rknn_set_core_mask` 的绑定真实生效，且**三颗核心算力等价**（与 3.2 一致）。

## 五、模型转换环境的落地调查（2026-09-13 实测）

§5 能不能在本机做，查清了三条：

| 路径 | 实测结果 |
|---|---|
| **官方 Windows 轮子** | ❌ **不存在**。GitHub `rknn-toolkit2/packages/x86_64/` 只有 `manylinux_2_17_x86_64/manylinux2014_x86_64` 轮子；PyPI 的 `rknn-toolkit2` 同样只有 manylinux x86_64 / aarch64 两种 |
| **装到板子上转** | ❌ 那条 aarch64 轮子是给**同架构 Linux 主机**用的，转换时链接 x86_64 专用模拟器，装到 RK3588 板上也跑不了 |
| **厂商 rar 里的旧 Toolkit2** | ❌ `rknn-toolkit2.rar` 本体是坏的/残缺的（RAR5 头正常，但尾部不是合法结束块，7-Zip 26.03 的 `7zr` / `7za` 都报 `Cannot open the file as archive`）；且据已并入根 `../README.md` 的《NPU 开发环境》笔记记为 v1.3.0，只有 cp36/cp38 |
| **WSL2** | ✅ **最终路线**：装好后 `Ubuntu-2204` + rknn-toolkit2 2.3.2，转换 4.3 秒完成 |
| PC 网络 | ✅ 通 `raw.githubusercontent.com` / `pypi.org`，下载不受限 |

**结论**：转换这一步**卡在「缺一台 x86_64 Linux」**，不是网络、不是权限、不是版本问题。
最终用 **WSL2** 解决，详见 `../WSL/README.md`。

**顺带确认**：官方模型仓库 `rknn_model_zoo/examples/yolov5/model/` **只提供 ONNX**
（`download_model.sh` 就是拉 `yolov5s_relu.onnx`），CDN 上没有现成 `.rknn`
—— 所以 §9 的 119/181 fps 复现，绕不开上面任一条路。
